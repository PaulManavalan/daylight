# Calendar integration checkpoint

The web preview supports **reviewed file transfer**, a configurable [Google OAuth adapter](google-calendar.md) with reviewed reads/writes, and an iCloud CalDAV read adapter. Real account acceptance and continuous reconciliation remain unfinished. No provider password, public calendar URL, subscription fee or server-side token is required for the file bridge; the iCloud adapter uses an Apple app-specific password entered in Daylight.

1. Export the relevant private calendar as `.ics` using [Google Calendar on a computer](https://support.google.com/calendar/answer/37111) or [Apple Calendar on a Mac](https://support.apple.com/guide/calendar/icl1023/mac). Google ZIP exports must be extracted first. An iPhone-only calendar may need a different native/account-specific path later.
2. In `/day`, expand **Calendars**, choose the provider and a distinct name, then read the file. Review the times before clicking **Use these events**. Reading alone does not save or approve anything.
3. File imports cover a bounded 30-day window and retain source UID/occurrence identity. Reimporting the same name replaces that calendar's snapshot; other calendars remain separate. Local mode stays browser-local; signed-in focused screens use owner-bound account documents. Read times remain visible. Removing a saved read never deletes provider events.
4. The day engine blocks imported busy events, all-day events and overnight intervals. Exact duplicate UIDs/start times across calendars do not create duplicate local commitments. Overlaps remain protected and are reported. Changes to imported calendars invalidate the current draft or approval.
5. Approve a Daylight plan before exporting `.ics`. The default export includes only Daylight focus sessions. A separate opt-in export also includes explicitly chosen training blocks: no external appointments, attendees, invitations or alarms. UTC timestamps and deterministic UIDs are used. A download is not proof of provider acceptance. Repeated manual imports may create duplicates in external calendar apps.

Recurrence expansion uses maintained `ical.js`, including exclusions, canceled and moved exceptions and embedded timezone rules. Unknown TZIDs without definitions, invalid durations, orphan overrides, high-frequency/unbounded expensive expansions, invitation files and oversized files fail rather than silently free up time. Floating times use the device timezone with an explicit review warning. Date range expiry blocks planning until the source is refreshed. Imported calendar content is data, not AI instructions; attachments, links and remote content are not fetched or executed.

## Live integration work remaining

- Google: OAuth/refresh, reviewed range reads and receipt-based writes are now implemented; real account testing, durable server token storage, automatic source reconciliation, incremental synchronization and cross-device selections remain. No credentials or account authorization are configured by this change. See [the implemented adapter and launch gates](google-calendar.md), [scopes](https://developers.google.com/workspace/calendar/api/auth), and [sync tokens](https://developers.google.com/workspace/calendar/api/guides/sync).
- Apple: iCloud account support now uses a CalDAV read adapter and a reviewed source snapshot. Event creation/editing, a durable cross-device credential vault and automatic reconciliation are not implemented yet. Device-only calendars would need a native route such as [EventKit](https://developer.apple.com/documentation/eventkit/accessing-the-event-store). This is not a generic Apple Calendar OAuth API and does not require publishing a private home calendar.

## iCloud read connection

Open `/day/preferences#icloud-calendar`. Apple documents [app-specific passwords](https://support.apple.com/en-us/102654) for third-party access and requires two-factor authentication to generate them. Enter the account email and an app-specific password in Daylight, never the main Apple password. The server validates principal/home discovery and lists calendars before storing a connection. Choose one calendar and a window of up to 32 days; review the returned events before **Use reviewed iCloud events**. Reading alone never replaces planner data. A failed read or browser disconnect preserves the last saved snapshot.

Server-only configuration is `ICLOUD_CALENDAR_ORIGIN` and a separate random `ICLOUD_CALENDAR_COOKIE_SECRET` of at least 32 characters. The local preview's canonical origin is `http://127.0.0.1:3104`; hosted configuration must use HTTPS. Actual account credentials do not belong in environment variables or repository files. They are sealed into an owner-bound, expiring, HttpOnly, scoped browser cookie using AES-256-GCM and never enter localStorage, account documents, planner backups or API responses. Disconnect removes that browser's connection; revocation of the app-specific password happens at Apple. Another browser needs its own connection.

Network requests are restricted to fixed Apple CalDAV hosts, including each manual redirect. Discovery and reads use bounded namespace-aware XML with entity/declaration rejection, response size/count limits and a request deadline. All-day and floating event times use the explicitly requested display timezone, independent of the hosting server; ambiguous clock-change times fail for review. Stable source IDs replace the same calendar even if its display name changes. Google/iCloud source reads and file imports are labeled separately; none is represented as continuous background synchronization.

Collections that explicitly support only tasks or other non-event components are excluded from the event calendar picker. The discovered DAV permission metadata recognizes full access as well as write privileges; this metadata does not enable writes in the read-only adapter. Refresh errors use the saved display name when one is available.

The synthetic server and browser checks cover discovery, redirect credential confinement, malformed XML, owner/expiry/tamper checks, origin/body guards, read review/cancel, failed-read preservation, credential exclusion from exports, preferences merging and protected day planning. Apple's discovery endpoint returned HTTP 401 to a request without credentials on November 24; this proves endpoint reachability, not authenticated account acceptance. A real user-authorized calendar read remains required. Protocol references: [CalDAV RFC 4791](https://datatracker.ietf.org/doc/html/rfc4791) and [current-principal RFC 5397](https://datatracker.ietf.org/doc/html/rfc5397).

No paid service is introduced. Account setup, provider quotas/verification, hosting behavior and actual end-to-end authorization must be checked before claiming live sync.
