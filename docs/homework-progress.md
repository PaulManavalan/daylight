# Reviewed homework progress

Daylight can turn a clear conversational homework report into a short, editable review. Nothing is recorded until the user clicks **Record this check-in** or explicitly confirms the current review. An unrelated later “yes,” a question, elapsed timetable time, and hypothetical discussion do not approve a report. The optional manual check-in uses the same reviewed save path.

Reports distinguish actual minutes already worked from focus minutes still wanted today. Completing a suggested focus block does not mean finishing an assignment. Unreported actual time remains unknown. A focus-time change adds no actual work. Reports apply to Daylight only; Notion and calendars stay unchanged.

After recording, the scheduler credits explicit actual work against the day's focus allowance and proposes a fresh timetable from the remaining window. That timetable requires its own approval. A saved report survives an ended work window even when no new timetable can be made. Records can be removed after a separate review, restoring the remaining-focus calculation.

The saved-day payload carries source provenance, immutable record identities, the pending review and its source/work revision. Refreshed or concurrently changed records invalidate old approvals. Portable restore and local-to-account copy clear pending conversational reviews. Account restore also clears timetable approval. Existing backups without these fields load with an empty log. Midnight, interrupted restores, concurrent writes and storage failures cannot silently apply the pending report.

The small local model sometimes abstains on literal completion reports. A narrowly bounded fallback recognizes an explicit completion statement naming one exact, unique source title and produces an **unsaved** proposal. It does not guess partial titles or resolve duplicate names. The model still interprets other work reports; grounding validates source keys, explicit quantities and outcomes. False save claims and reproduced hypothetical completion/card claims are rejected; reply generation gets at most one repair attempt, with no repeated extraction or write.

Verification uses synthetic records. Domain tests cover stale reviews, provenance, unknown time, actual versus remaining work, removal and backup compatibility. Browser checks cover review edits, reload, unrelated confirmation, failed storage saves, midnight, a revised draft and mobile layout. Installed Gemma evaluations cover completion, more-time, actual-work and hypothetical conversation; these are bounded examples, not universal model reliability. Real hosted WebGPU inference remains unverified because the approved model's weight host failed in this environment. Real provider/account acceptance remains a separate launch gate.

The November 22 checkpoint passes 296 unit tests and a production build. The real Supabase browser SDK with a synthetic backend verifies that reviewed work reaches a second device for the same account, invalidates the prior timetable approval and remains absent from another account. Existing focused planning, source-refresh, conversation-preservation, backup, Today and news browser checks also pass. No real account credentials or personal source records were used for these checks.

## Conversational follow-through

A broader installed-model evaluation exposed compound durations losing their total, corrections being dropped, and a subject clarification losing its original completion report. Duration grounding now preserves an explicit hour-and-minute interval separately from remaining focus. An unambiguous numeric correction applies only to the current unsaved review. Duplicate titles require a unique subject or the current review's identity; the review card displays the subject.

An immediate short answer to a subject or actual-duration question stays attached to the explicit work report. Open chat, questions, unrelated events and a bare “yes” cannot serve as that clarification. Literal completion recovery also handles an exact subject-qualified title and the exact subject answer to a duplicate-title clarification. These are still unsaved proposals, never automatic work records.

Eight synthetic real-model cases pass, including duplicate-title clarification, subject-qualified completion, a one-word subject answer, a worded duration answer, unfinished work, unrelated conversation, numeric correction and compound actual time. A separate isolated browser uses the actual local AI endpoint for duplicate titles → one-word answer → review → recording, then compound duration → correction → review → adaptive draft. This passes without mocked model replies or Notion writes. The real browser check is opt-in via `DAYLIGHT_REAL_MODEL_TEST=1`; it uses the existing installed local model and synthetic data only.

The planner also shows current and next blocks from an approved timetable, including breaks and open time. It lists overlapping active commitments instead of hiding one, stops showing a current action when the plan belongs to another day, and refreshes the clock while the page is open. Clock movement never changes approval, work records or saved data. Boundary, midnight, mobile and reduced-motion browser checks pass, alongside 303 unit tests and the production build.
